# Story 4.1: Motion and reading polish

- Epic: Epic 4: Polish
- Status: ready-for-dev

## Story

As a visitor, I want navigation and long reads to feel smooth and to show me how far I am through an article
or project, so that the site feels finished and I can pace my reading.

## Acceptance criteria

1. **Page transitions.** Navigating between pages runs the DESIGN.md › Movimento page transition: the old
   page fades out, the new page fades in rising from `translateY(8px)`, ~300ms,
   `cubic-bezier(0.16, 1, 0.3, 1)`. The header does not animate. Browsers without View Transitions navigate
   normally (no fallback, no error).
2. **Smooth scrolling.** In-page anchor links (for example the header links to `/#projects`, `/#articles` and
   "Back to articles") scroll smoothly (`scroll-behavior: smooth` on `html`).
3. **Custom scrollbar.** On every page the root scrollbar is thin, with the track in `background`, the thumb in
   `border` with `full` radius, and the thumb in `muted-foreground` on hover (`scrollbar-width` /
   `scrollbar-color`, plus `::-webkit-scrollbar` where needed).
4. **Reading-progress bar.** On `/article/<slug>/` and `/project/<slug>/` only: a 2px bar fixed to the top of
   the viewport, gradient `accent`→`primary`, whose width is the fraction of the document scrolled (0% at the
   top, 100% at the bottom; 0% when the page does not scroll). It is decorative: `aria-hidden="true"`, not
   focusable, and it does not cover or intercept clicks on the header. It does not appear on the home, CV or
   404 pages, or in print.
5. **Reduced motion.** With `prefers-reduced-motion: reduce`: no page transition, `scroll-behavior: auto`. The
   progress bar still tracks position but does not animate its width.
6. **Playwright** (`[story 4.1]`): the progress bar exists on a fixture article and a fixture project and is
   absent on home and CV; its width grows after scrolling to the bottom; `html` computes
   `scroll-behavior: smooth` normally and `auto` under `reducedMotion: 'reduce'`; the root
   `scrollbar-width` is `thin`. Page transitions: assert the view-transition styles are present and do not
   break navigation (a click to a project still lands on it); the visual motion itself is not asserted.

## Open technical question (resolve before coding; architecture skill if it needs a decision)

Next.js `<Link>` does soft (client-side) navigation, so CSS cross-document `@view-transition { navigation: auto }`
alone will not animate those navigations. The options are Next's `experimental.viewTransition` with React
`<ViewTransition>`, or `document.startViewTransition` around router navigation. Turning on an experimental
framework flag is an architecture decision: propose it to `bmad-architecture` (D-series) instead of enabling it
inline, and note the outcome here.

## Dev notes

- **Open technical question resolved by the installed stack (no architecture entry needed).** React 19.3
  ships `<ViewTransition>` as a stable export and the installed Next 16.4 docs
  (`next/dist/docs/01-app/02-guides/view-transitions.md`) state view transitions work in the App Router
  "with no configuration". No `experimental.*` flag and no `document.startViewTransition` wrapper: the
  `(site)` layout wraps the page in `<ViewTransition default="page">`, and `globals.css` styles
  `::view-transition-old/new(.page)`. Verified in Chromium that a home → project navigation runs
  `page-fade-out` / `page-rise-in` on the page content and no animation on the header.
- **Deviation from AC 3 / AC 6 (user decision, 2026-11-09).** Since Chrome 121 `scrollbar-width` /
  `scrollbar-color` disable `::-webkit-scrollbar` styling, so the thumb hover state would be lost in
  Chromium. The standard properties live in `@supports not selector(::-webkit-scrollbar)` (Firefox only,
  no hover change); every other browser uses `html::-webkit-scrollbar*` (8px, track `background`, thumb
  `border` with full radius, `muted-foreground` on hover). AC 6 is amended accordingly: the Chromium spec
  asserts the webkit rules (including `::-webkit-scrollbar-thumb:hover`) exist and that the root does not
  compute `scrollbar-width: thin`.
- `data-scroll-behavior="smooth"` on `<html>` makes Next 16 drop smooth scrolling during route changes, so
  new pages open at the top instantly while anchors scroll smoothly.
- `view-transition-name` makes the header a stacking context, which put the mobile menu panel (`z-40`
  inside the header) under `<main>` and broke the story 2.1 mobile-menu spec. The header now carries
  `z-40` itself.
- The progress bar is located by `getByTestId('reading-progress')` in e2e: it is `aria-hidden`, so it has
  no role or name (documented in the specs and the `SiteShell` page object). Width uses `scaleX` (compositor
  only); the bounding box still reflects progress. New tokens in `@theme`: `--ease-standard`
  (`cubic-bezier(0.16, 1, 0.3, 1)`) and `--duration-page` (300ms).
- Specs: `e2e/shell/motion.spec.ts`, `e2e/article/reading-progress.spec.ts`,
  `e2e/project/reading-progress.spec.ts` (also covers absence on home, CV and 404); unit
  `src/shared/lib/scroll-progress.test.ts`. All written first and seen failing.
- Review round: `motion.spec.ts` now records `document.getAnimations()` during a home → project navigation
  and asserts `::view-transition-new(...)` plays `page-rise-in` (fails with `default="none"`). Reduced
  motion: headless Chromium records no view-transition animation under `reducedMotion: 'reduce'` even
  without the CSS opt-out, so that case is asserted from the CSSOM (the reduced-motion media rules list
  `::view-transition-{group,old,new}` for `(*)` and `(.page)`); `(*)` also stops the browser's default
  root crossfade.
- Not covered: Firefox (only Chromium runs, so the `@supports` scrollbar branch is untested), and
  Lighthouse was not re-run for this story.
- Fix after release (2026-11-09, `9ecfb27`), reported as "page transition not working":
  1. The header section links are plain `<a href="/#…">`, so leaving an article/project through them was
     a full page load with no transition. Added cross-document `@view-transition { navigation: auto;
     types: page-load }` with the same fade-and-rise on `::view-transition-{old,new}(root)` under
     `:active-view-transition-type(page-load)`; `navigation: none` under reduced motion.
  2. The `<ViewTransition>` in `(site)/layout.tsx` wrapped several top-level sections, so React named each
     one and they faded separately (up to 7 groups). Wrapped `children` in one `div`.
  Specs: "moves the whole page content as one piece" (records animations); the full-load case is
  asserted from the CSSOM because headless Chromium skips some cross-document snapshots at random
  (`pagereveal` without `viewTransition`, also serially, ~1 in 3–5). Live check: soft navigation 5/5
  as one piece; header link 3/5 animated in headless Chromium. Firefox has no cross-document view
  transitions, so header links stay instant there.
