# Story 3.1: SEO, feeds and redirects

- Epic: Epic 3: SEO and launch
- Status: review

## Story

As the site owner, I want search engines and feed readers to find the new site exactly like the old one, so that no traffic is lost at cut-over.

## Acceptance criteria

1. Metadata per page: title template, description, canonical (`siteUrl` + path with trailing slash), Open Graph + Twitter card (cover/portrait image), `lang="en"`.
2. JSON-LD: `Person` on `/`, `Article` on articles, `CreativeWork` on projects.
3. `/sitemap.xml` lists `/`, every project and article URL (absolute, trailing slash, lastmod); `/robots.txt` allows all and points to the sitemap; `/cv/` excluded.
4. `/feed.xml`: RSS 2.0 of articles (title, link, guid, pubDate, description).
5. `out/_redirects` generated from `content/settings/redirects.yml` (D4); under `wrangler dev`, `/feed/` and `/wp-sitemap.xml` answer 301 to the new URLs.
6. A parity script `pnpm --filter web verify:parity <baseUrl>` fetches every URL of the old `wp-sitemap.xml` (recorded list committed in `apps/web/scripts/legacy-urls.txt`) against `<baseUrl>` and fails unless each answers 200 (or 301 to a 200).
7. Playwright specs for metadata, sitemap, robots, feed and redirects.

**What was built**

- AC1: `buildPageMetadata` (`shared/lib`) now returns title, description, `alternates.canonical`
  (`siteUrl` + trailing-slash path), Open Graph (`website`, or `article` with `publishedTime`) and a
  Twitter card (`summary_large_image` with an image, `summary` without). Used by `/`, projects,
  articles and `/cv/`. Images: project cover; article cover, else the portrait; portrait on `/`.
  `lang="en"` was already on `<html>`; the root layout now sets `metadataBase`. The home title is the
  bare site name (as on WordPress), via `title: null`.
- AC2: `features/seo` builds `Person` (`/`), `Article` and `CreativeWork` JSON-LD; `shared/ui/JsonLd`
  renders them. **Approach:** the JSON is the React text child of
  `<script type="application/ld+json">`, serialized by `serializeJsonLd`, which replaces every `<`
  with `\u003c` (still valid JSON, can never close the script). No `dangerouslySetInnerHTML`.
  Verified that React 19 writes script text children without entity-escaping, so the served JSON parses.
- AC3: `app/sitemap.ts` and `app/robots.ts` (metadata routes, `dynamic = 'force-static'`) export to
  `out/sitemap.xml` and `out/robots.txt` under `trailingSlash: true`. `/cv/` is not in the sitemap; it
  is **not** disallowed in robots.txt on purpose (a crawler must fetch it to see its `noindex`).
- AC4: `app/feed.xml/route.ts` (`force-static`) exports `out/feed.xml`: RSS 2.0, a hand-written
  template with XML escaping (no new dependency), `atom:link rel=self`, items newest first with
  title, link, `guid isPermaLink="true"`, RFC 822 `pubDate`, description = summary.
- AC5: `scripts/redirects-step.ts` (D4 step 1, before `cvPdfStep`) writes `out/_redirects`
  (`/from /to status`) from `settings/redirects.yml`, validated with the contracts schema. tsx does
  not resolve `@/`, and `@/shared/content` imports `server-only`, so the step uses relative imports of
  `content-source.ts`, the redirect mapper and a new dependency-free `shared/content/content-dir.ts`
  (`resolveContentDir`, now also used by `shared/content/index.ts`, so both honor `CONTENT_DIR`).
- AC6: `pnpm --filter web verify:parity <baseUrl>` (`scripts/verify-parity.ts`, logic in
  `scripts/parity-check.ts`, unit-tested with an injected fetch). Paths in
  `apps/web/scripts/legacy-urls.txt`. Each must answer 200, or 301/308 whose Location answers 200
  (at most 2 hops); prints a table, exits 1 on any failure.
- AC7: `e2e/seo/{metadata,structured-data,sitemap-robots,feed,redirects}.spec.ts`, tagged
  `[story 3.1]`, critical paths `@smoke`. Meta tags and JSON-LD are read from the served HTML
  (`e2e/pages/served-html.ts`), following the story 2.3 precedent: they have no ARIA role.

**Decisions**

- Legacy URLs, recorded once from the live `wp-sitemap.xml` (read-only, 2026-11-08): home (1),
  projects (3), posts (5), plus `/feed/` and `/wp-sitemap.xml`. `wp-sitemap-users-1.xml` and
  `/author/*` answer 404 on WordPress, so there are no author archives. The sitemap also lists
  **taxonomy archives that answer 200 on WordPress**: `/article/category/uncategorized/` (1),
  `/article/tag/<slug>/` (21), `/project-tag/<slug>/` (9). The PRD excludes index pages, so they are
  kept in `legacy-urls.txt` and **redirected** by three splat rules added to
  `content/settings/redirects.yml`: `/article/category/*` and `/article/tag/*` to `/#articles`,
  `/project-tag/*` to `/#projects` (301). Cloudflare keeps the fragment in `Location`. The migrator
  merges redirects and keeps existing ones, so a re-run does not drop them.
- Sitemap `lastmod`: articles use `publishedOn`. The content model has no "updated on" date, so `/`
  and projects use the build date. If real modification dates are wanted, an `updatedOn` field is a
  model change to propose through `bmad-architecture`.
- Content types under `wrangler dev`: `feed.xml` and `sitemap.xml` are `application/xml`,
  `robots.txt` is `text/plain; charset=utf-8`. WordPress served the feed as `application/rss+xml`.
  A `_headers` rule could match that; I left it out because `application/xml` is valid for RSS.
- The live robots.txt also has a "Cloudflare Managed Content" block (AI-crawler rules) added by the
  zone, not by WordPress. Our `robots.txt` allows all and points to the sitemap. Whether the zone
  setting still prepends its block on the Workers origin should be checked at cut-over (story 3.3).
- `feed.xml/route.ts` must export `GET`, which breaks `useNamingConvention`; it carries a
  `biome-ignore` with the reason instead of loosening the config.
